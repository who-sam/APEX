Compiler & Grader

Speaker: [Member 2] · ~4 minutes
Compiler · Why

Why we run student code in a sandbox.

The naive approach

Run student Python with exec() in the server process. Instant RCE — they can read your DB credentials, your secrets, the OS.

The compromise approach

Compare student output to expected output by string match. Works for trivial cases. Falls apart on whitespace, newlines, locale, runtime errors.

What we did

  • Judge0 CE — open-source code sandbox.
  • Isolated Linux container per submission.
  • Resource limits: CPU time, wall time, memory, output size.
  • Returns structured status: Accepted, WA, TLE, MLE, CE, Runtime Error.
  • 6 languages supported: Python, JS, TS, Java, C, C++.
Frame it as a security choice first, then a correctness choice. Mention you can self-host Judge0 for production. The public ce.judge0.com is rate-limited and only fine for demo.
Compiler · Pipeline

Submission pipeline

// internal/judge0/client.go
var LanguageMap = map[string]int{
    "python": 100, "javascript": 102, "typescript": 101,
    "java": 91, "c": 103, "cpp": 105,
}

func RunCode(code, language, stdin string) CodeResult {
    langID := LanguageMap[language]
    body, _ := json.Marshal(request{LanguageID: langID, SourceCode: code, Stdin: stdin})
    resp, _ := http.Post(BaseURL+"/submissions?wait=true&base64_encoded=false", ...)
    // returns {stdout, stderr, status, time, memory}
}

Per submission

  • Marshal source + stdin to JSON.
  • POST to Judge0 with wait=true — synchronous.
  • Parse time (seconds → ms), memory (KB).

Status mapping

3 = Accepted 4 = Wrong Answer 5 = TLE 6 = CE 11 = Runtime Error
Walk through one round-trip. Mention the choice of synchronous wait — simpler than polling, fine for our scale. Async/queue would be next step for production.
Compiler · Grading

Per-test grading with output normalization

// internal/judge0/grader.go
for _, tc := range testCases {
    result := RunCode(submission.Code, submission.Language, tc.Input)
    actual   := normalizeOutput(result.Stdout)
    expected := normalizeOutput(tc.ExpectedOutput)
    isPassed := (result.StatusID == 3 || result.StatusID == 4) && actual == expected
    if isPassed { passed++ }
    // ... persist TestResult
}
score := float64(passed) / float64(total) * 100.0

Output normalization

  • \r\n → \n (CRLF strip)
  • Trim trailing whitespace per line
  • Trim leading/trailing newlines

Without this: 80% of "wrong answers" are formatting differences.

Three grading paths

  • Coding → Judge0 per test case
  • MCQ → set-equality on correct_option_ids
  • Written → pending_review, teacher grades manually
Normalization story is worth telling — we hit it the first time we tested with a Windows-saved file. \r\n broke everything. Now part of the standard pipeline.
Compiler · Aggregation

The pending-review aggregation problem

Naive aggregation breaks the display

Student answers 3 coding (auto-graded) + 1 written (pending). If we average across all 4, written = 0 → score looks like 75% until teacher grades. Student panics.

Our fix: exclude pending_review from both numerator and denominator

for _, p := range problems {
    s, hasSub := subByProblem[p.ID]
    if hasSub && s.Status == "pending_review" { continue }
    totalPoints += float64(p.Points)
    if hasSub { earnedPoints += s.Score / 100.0 * float64(p.Points) }
}

Skipped questions still count as 0/total. Pending-review = invisible until graded. Re-aggregates automatically when teacher submits the grade.

This is the kind of bug you only catch by actually using the product. Mention: idempotent notification via graded_notified column means students get exactly one "Exam Graded" notification, even if re-aggregation fires multiple times.

Database · Incident

The day every exam disappeared

// What we added
type Exam struct {
    // ...
    IsDraft bool `gorm:"default:true"`  // ← seemed harmless
}

What actually happened

  • GORM AutoMigrate added the column.
  • Set every existing row to is_draft = true based on the default.
  • Student queries filter WHERE is_draft = false.
  • Every exam vanished from every student dashboard. Silently.

Lesson learned

ORMs make schema look like code. But schema is state. You can't refactor state with a struct tag.

Be honest about it — we hit this in prod-ish demo with seeded data. Wrote ORM_RULES.md the same day. The incident drove the whole migration policy.
Database · Policy

Two-pass migrations · explicit then automatic

The pattern: add → backfill → constrain

-- 1. Add nullable
ALTER TABLE exams ADD COLUMN IF NOT EXISTS
  is_draft BOOLEAN;

-- 2. Backfill with the CORRECT value
UPDATE exams SET is_draft = false
  WHERE is_draft IS NULL;

-- 3. Constrain
ALTER TABLE exams ALTER COLUMN is_draft
  SET NOT NULL;
ALTER TABLE exams ALTER COLUMN is_draft
  SET DEFAULT false;

Two execution paths

Local dev → migrations.go runs explicit SQL before AutoMigrate.

Production → SKIP_AUTOMIGRATE=true. Versioned SQL files in migrations/sql/NNNN_*.up.sql via golang-migrate.

Idempotent Forward + backward No surprise defaults

Security

Speaker: [Member 5] · ~4 minutes
Security · Authentication

JWT + bcrypt + Google Identity

Password sign-in

  • bcrypt at default cost
  • HS256 JWT, 24-hour expiry
  • Claims: user_id · email · role · name · exp

Fail-fast secret check

if jwtSecret == "" ||
   jwtSecret == "dev-secret-change-in-prod" ||
   len(jwtSecret) < 32 {
    log.Fatal("JWT_SECRET must be set ≥32 chars")
}

Server refuses to start with a weak secret. Cannot accidentally deploy to prod with dev defaults.

Google Identity Services

  • Server-side idtoken.Validate against Google's public certs
  • Links by google_id, falls back to email
  • Only verified emails accepted

Password reset

  • 32-byte random token, SHA-256 hashed at rest
  • 1-hour expiry, single-use
  • "If account exists" response — no email enumeration
Lead with the fail-fast — it's the strongest one-liner. Most projects let dev secrets leak into prod. We made it impossible.
Security · Authorization

Two-layer RBAC. Server is authoritative.

// Layer 1: middleware extracts JWT, sets user_id and role on context
protected.Use(middleware.Auth(cfg.JWTSecret))

// Layer 2: route groups gate by role
exams := protected.Group("/exams")
exams.Use(middleware.RequireRole("teacher"))   // returns 403 otherwise
exams.PUT("/:id", UpdateExam)

Frontend mirrors, but never owns

TeacherRoute / StudentRoute redirect on role mismatch — UX only. Tamper with localStorage, browse to a teacher route → API still returns 403.

Three role checkpoints

  • JWT signature → who you are
  • JWT role claim → what you are
  • Query WHERE clause → what you own
Frontend route guards are UX. Backend role middleware is security. Don't conflate them.
Security · IDOR

IDOR by design · ownership in the WHERE clause

❌ Vulnerable pattern

var exam models.Exam
db.First(&exam, examID)  // any ID works
db.Model(&exam).Updates(updates)
// Teacher A can edit Teacher B's exam.

✓ Our pattern (everywhere)

var exam models.Exam
db.Where("id = ? AND teacher_id = ?",
        examID, teacherID).First(&exam)
// Returns 404 if not owner. Single query.

Cross-resource ownership: AssignExam

// Before linking exam → classes, verify EVERY class_id belongs to caller
db.Model(&models.Class{}).
   Where("id IN ? AND teacher_id = ?", req.ClassIDs, teacherID).
   Count(&ownedCount)
if int(ownedCount) != len(req.ClassIDs) {
    c.JSON(403, gin.H{"error": "one or more classes do not belong to you"})
}
IDOR = Insecure Direct Object Reference, top-5 OWASP. We never trust an ID from the client — every fetch is scoped to the caller's ownership in the same query.
Security · Defense in depth

Hardening across the stack

Transport & origin

  • CORS allowlist from APP_URL + ALLOWED_ORIGINS, never *
  • Credentials disabled in CORS config
  • HTTPS terminated at reverse proxy in prod

Code execution

  • Student code never runs in our process
  • Judge0 isolated container per submission
  • CPU + memory + wall-time limits enforced

Data integrity = security

  • Schema migration rules prevent silent state corruption
  • Account deletion is a transaction with explicit cascade
  • Reset tokens invalidated on new request
  • Idempotent notifications prevent spam-on-retry

No secrets in repo

  • .env.example only, real .env in .gitignore
  • CI uses GitHub Actions secrets

The Problem

Assessing programming skill with paper and general-purpose tools breaks down in three ways.

01

Code that never runs

Paper exams and generic form tools can't execute a student's program — correctness is judged by reading, not by running.

02

Slow, inconsistent grading

Hand-grading code for a full class takes days, and two graders rarely score the same answer the same way.

03

Fragile timed attempts

In the browser, a refresh or crash can wipe answers or reset a timer — a timed exam has to survive failure.

  • امتحان البرمجة محتاج تلات حاجات مش موجودة في الورق والأدوات العامة
  • الكود لازم يشتغل فعلاً، مش بس يتكتب
  • التصحيح لازم يبقى موحّد وعادل، مش مزاجي وبطيء
  • الوقت لازم يفضل آمن حتى لو النت وقع من الطالب
  • كل وجع فيهم بيتحل في جزء من APEX هنوريه

The Solution

APEX — a full-stack classroom exam platform. Build, run, and auto-grade coding exams in the browser.

Teachers build

Three question types

Coding, MCQ, and written questions, assembled into exams and assigned to classes.

Students take

Timed attempts, in the browser

Code is written in a Monaco editor — VS Code's engine — inside a crash-safe, autosaving runner.

APEX grades

Isolated auto-grading

Coding answers execute in a Judge0 sandbox against hidden test cases. MCQ is auto-graded; written is graded manually.

The Crash-Safe Exam Runner

~1,170 lines built around one promise: a refresh, crash, or dropped connection cannot cost a student their exam.

Monaco editor

VS Code's editor engine — syntax highlighting and a real coding surface in the browser.

Derived timer

Remaining time is computed from startedAt — a refresh cannot reset the clock.

Dual-layer autosave

localStorage on every keystroke + a 1.5s debounced PUT to the server.

~1,170-line crash-safe runner

Reload mid-exam → answers and clock restore exactly where you were.

  • أعمق شغل في الـfrontend، وعده: refresh أو نت واقع أو هنج ما يخسّرش الطالب امتحانه
  • الوقت بيتحسب من الـstartedAt على السيرفر — مفيش حاجة في المتصفح تصفّر العداد
  • الإجابة بتتحفظ مرتين: محلياً مع كل حرف، وعلى السيرفر كل 1.5 ثانية بالـdebounce
  • في الديمو: هنعمل refresh وسط الامتحان ومش هيضيع حاجة

Defense in Depth

Eight independent controls between an attacker and the data.

ring 1
Strict CORS  ·  parameterized queries
only known origins; no string-built SQL
ring 2
JWT HS256 pinned to HMAC  ·  bcrypt
pinning blocks algorithm-confusion attacks
ring 3
RequireRole  ·  per-owner query scoping
wrong role or wrong owner → request dies early
ring 4
Hidden test cases withheld  ·  fail-closed secrets
the browser never receives expected outputs
most prominent

HS256 pinned to HMAC — forged-algorithm tokens rejected.
Fail-closed boot — JWT_SECRET < 32 chars → refuses to start.

  • مفيش خط دفاع واحد: تمن طبقات مستقلة بين المهاجم والداتا
  • الـedge: CORS وqueries كلها parameterized (مفيش injection)
  • الهوية: JWT متثبّت بالـHMAC، والباسوردات bcrypt
  • الصلاحيات: RequireRole و owner scoping
  • المحتوى: test cases مخفية وأسرار fail-closed
  • النبضة الحمرا = هجمة بتموت عند أول طبقة — خلّي بالكم من الحاجتين الكبار، السلايد الجاي هيفصّلهم

Inside the Five Layers

What each control in the chain actually does — from the edge to the sandbox.

EdgeCORS Allowlist
Only requests from origins on a predefined allowlist reach the API — any other website is blocked before it touches a handler.
IdentityJWT + HMAC
On login the server issues a token — user id, role, expiry — signed with a secret key. Every request re-verifies the signature, so a tampered or forged token is rejected.
AuthorizationRequireRole (RBAC)
Middleware checks the token's role before any handler runs — teacher-only routes reject a student, and vice-versa.
DataPer-Owner Scoping
Every database query is scoped to the authenticated user — you only ever read your own rows, never an ID the client claims to own.
ContentJudge0 Sandbox
Student code runs in an isolated sandbox with strict CPU, memory, time and filesystem limits — even malicious or infinite-loop code can't reach the main server.
  • دي تفاصيل الطبقات اللي شفناها في السلايد اللي فات — كل واحدة بتعمل إيه بالظبط
  • Edge — الـCORS بيسمح بس للمواقع اللي في الـallowlist توصل للـAPI
  • Identity — JWT متوقّع بـHMAC بمفتاح سري، وأي token متزوّر أو متعدّل بيترفض
  • Authorization — الـRequireRole بيتأكد من دور اليوزر قبل أي handler
  • Data — كل query مربوطة باليوزر نفسه، فمحدش يقرا داتا غيره
  • Content — كود الطالب بيتنفّذ جوه Judge0 sandbox بحدود CPU وميموري ووقت وملفات

Attacks That Don't Work

We built it assuming someone will try to cheat or break in — here's what happens when they do.

✗A student opens another student's submission by ID
→
✓Every read is owner- / enrollment-scoped — the API returns 403, never someone else's row
✗Scrape the hidden test cases to hard-code the outputs
→
✓Hidden cases never reach the browser — /run returns sample tests only
✗Forge a JWT with alg: none or RS256
→
✓The verifier pins the HMAC family before the signature is even checked
✗Student code tries to read the database or filesystem
→
✓It executes inside the Judge0 sandbox — never on our server
✗Skip the hard questions to inflate the score
→
✓The denominator is the full problem list — a skipped question scores 0
  • بنيناه وإحنا فاكرين إن حد هيحاول يغش أو يخترق — دي أمثلة لهجمات وبتفشل ليه
  • طالب يفتح submission بتاع زميله بالـID؟ كل قراءة مربوطة بصاحبها → بيرجّع 403
  • يسحب الـhidden test cases؟ عمرها ما بتوصل للمتصفح، والـ/run بيرجّع الـsample بس
  • يزوّر JWT بـalg none أو RS256؟ بنثبّت عيلة HMAC قبل ما نتحقق من التوقيع أصلاً
  • كود الطالب يحاول يقرا الداتابيز أو الملفات؟ بيتنفّذ جوه Judge0 sandbox، عمره ما بيلمس سيرفرنا
  • يسيب الأسئلة الصعبة عشان الدرجة تعلى؟ المقام هو كل المسائل، والسؤال المتسايب بياخد صفر
  • تسليم: M5 هيوريكم التغليف والاختبار والنتايج

Hardened Image

The production container ships with less, on purpose.

distroless

No shell, no package manager

The runtime image contains the Go binary and its certificates — an attacker who lands inside finds nothing to run.

non-root

Unprivileged by default

The process runs as a non-root user, so a container escape starts from the weakest possible position.

--healthcheck

The binary probes itself

No curl or wget in a distroless image — so the health check is baked into our own binary as a self-probe flag.

HEALTHCHECK CMD ["/app/server", "--healthcheck"]  # the same binary, probing itself
  • الـproduction image مقصودين نخليه أنحف: مفيش shell ومفيش package manager
  • بيشتغل unprivileged افتراضيًا — حتى لو حد دخله مش هيلاقي أدوات
  • نتيجة الـdistroless: مفيش curl للـhealthcheck
  • زوّدنا للـbinary فلاج ‎--healthcheck بيجرّب الـendpoint بنفسه ويرجّع نجاح/فشل
  • تفصيلة صغيرة بتوري إن التغليف اتفكّر فيه من الأول للآخر
